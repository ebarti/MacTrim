# Lightweight storage history and growth detection

User steering on 2026-10-03: disk use grew from about 380 GB to over 450 GB; add historical usage/growth detection to spot storage leaks. History must use very little disk. Extend the current upgrade and existing private PR (shared storage collector/UI contract); do not stop the original cleanup/TUI/graph/list work.

First principles: a measured historical delta needs two comparable observations. File timestamps can suggest recent activity but cannot reconstruct a missing previous directory-size baseline, distinguish old deleted data, or measure bytes added. APFS filesystem capacity and directory allocation estimates are different observations. Unknown/partial coverage must not become asserted growth. History is read-only evidence, never cleanup authorization.

Live baseline evidence gathered by main: os.statvfs on /, /System/Volumes/Data and /System/Volumes/VM currently returns identical 494384795648 total, 458674102272 reported used and 35710693376 available bytes. Do not sum aliases/shared capacity. tmutil listlocalsnapshots / returned no Time Machine local snapshots; this does not prove absence of all APFS/system snapshots. User's earlier 380 GB is an approximate reported baseline, not a measured directory inventory.

## Accepted design

- Add a History/Growth view alongside Cleanup and Storage, and corresponding useful CLI capture/list/compare entry points. Show dates, filesystem used/free trend, largest comparable directory increases/decreases, absolute and percentage changes, sortable list plus library-based graph, and drill into a growing directory in Storage. Parent/child deltas overlap and must not be summed as independent growth.
- Establish and retain a real first baseline during verification on this Mac. Explicitly explain that prior 380 GB directory breakdown is unavailable. Recent creation/modification metadata can be a separately labeled clue: current bytes in recently created/modified files are NOT measured growth. Reuse existing metadata traversal to aggregate recent-activity buckets; do not hash/read file contents or do a second scan merely to record history.
- Snapshots contain timestamps, scope/policy/coverage, filesystem capacity, bounded directory aggregates (allocated/logical, completeness and stable identity as useful), and compact recent-activity summaries. Store directory totals only, no per-file inventories, file copies, logs or content hashes. Capture up to 5000 meaningful directory aggregates with bounded memory/encoded size, preferring useful large directories and keeping ancestors/root. Avoid a second expensive walk; augment collector outputs/callbacks as needed.
- Compare like scopes and compatible measurement policies; require comparable complete directory observations for asserted deltas. Missing/incomplete observations are unknown, never zero. A newly present directory is 'newly observed' unless the earlier parent enumeration was complete enough to prove absence. Root physical usage can still trend when directory attribution is partial; show the attribution gap without inventing a culprit.
- Default history disk budget: HARD 16 MiB total within its private history directory, including temporary files. Maximum 60 retained snapshots and 60-day age retention, configurable smaller limits/disable/clear. A compressed bounded JSON snapshot format using existing Python facilities is sufficient; avoid a large always-growing SQLite/WAL database or extra dependency. Reserve/prune space before writing an atomic snapshot, account actual allocated bytes, enforce max encoded/decompressed sizes and entry counts, handle interrupted writes safely, and expose actual history storage use/limit in UI/CLI. History failures must not break cleanup or root browsing.
- Automatic local capture only from already-performed suitable Storage measurements (with sensible dedup/rate limit); manual capture available. No recurring background full-disk scan, scheduler, launchd service or external notification is authorized/requested. Opening/revisiting the app can build history over time. Do not claim unattended monitoring is enabled.
- Private state permissions; history never committed/uploaded. Retention only touches owned, verified history records; unknown/symlink/unexpected files cannot be blindly erased. Detect snapshots altered or incompatible and report them safely. Use existing state signing/atomic utilities when helpful, without coupling history records to cleanup manifests or authorization.
